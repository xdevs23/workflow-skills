# The unit spec quotes the discussion

A unit spec of implement-review-verify holds the discussion of its unit, quoted verbatim from the
session transcripts, and nothing else. The orchestrating session no longer writes a spec: there
are no items, kinds, sources, derivations, criteria or summary, and the private directive record is
gone, because the spec itself now holds the user's words. The spec-writing skill is deleted, and
the rules for assembling the spec live in the section of the workflow skill on the unit spec. The
reviewers that judged the change per acceptance criterion now flag what is wrong by quoting the
user's words, and the fix list of a fix run names findings of the parent run by their source IDs
alone, so the fix run receives what the reviewers said.

## The spec file

A spec is a YAML file in the project cache with exactly two keys: `unit`, the unit's name, and
`entries`. Every entry has exactly five fields: `file`, `line` and `uuid` name one record of a
session transcript, `author` is `user` or `assistant`, and `text` is a verbatim substring of that
record. Only an entry of author `user` is authority. An entry of author `assistant` is context: it
gives the user entries after it their meaning, such as the explanation and the question a bare yes
answers, and decides nothing itself.

The spec starts at the message that the origin pointer of the unit's todo record names, since the
todo record is the first thing written when a unit is asked for. From there it holds every message
of the user about this unit, and of a message about two units only the part about this one, which
is why an entry quotes a substring and never has to hold a whole message. Assistant entries are
added only as far as the user's words need them. Entries keep session order, so a yes stays after
the question it answers.

The orchestrating session checks the spec with the spec tool and opens it in VSCodium for the user
to check. The user only removes entries that do not belong; nobody types into the file, so every
entry stays a quote the tool can verify against its record. The main run launches on the file as
the user leaves it.

A run's spec never changes, and no second run starts on the same spec. The discussion has no end:
words the user adds while a run is going or after it returns go into a copy of the spec, the same
file with the new entries appended under a new file name, and the next run starts on the copy. A
run that comes back with nothing built because the implementer flagged the spec continues the same
way, on a copy that holds the user's answer to the flag.

## What the spec tool checks

The spec tool refuses any top-level key but `unit` and `entries`, and any entry field but the five.
An entry of author `user` must quote a message the user wrote, typed or queued, or an answer the
user gave in the question dialog, including a note typed on it; a task notification, an injected
meta record, command output and the result of any other tool are refused, as before. An entry of
author `assistant` must cite an assistant record and quote its text blocks, the question text of
one of its dialog calls, or the content of one of its Write calls. A plan the user answered yes to
is therefore quotable when a Write call holds it. A file edited afterwards or generated by a
command has no record that holds its final text, so it reaches the stages only through the message
that pointed at it.

Entries of one session file never go back in line order; two entries may quote the same record.
A spec without an entry of author `user` fails. The width rule applies to the text of every entry:
quoted words keep their words, punctuation and order, while their line breaks are free, because the
tool compares them with the record after collapsing whitespace. The `--base` check of the
repositories, the `--partial-base` option, the `sha256`, the `unbreakable` list and the random
`proof` the launch check relies on are unchanged. The summary no longer carries counts or a list of
criteria, and the `--record` option is gone.

The `specLines` count behind the 20:1 size gate is the number of non-blank lines of the entries'
text. The gate itself is unchanged.

## What the stages receive

The shared authority block of both scripts states that the spec is the discussion of its unit,
quoted verbatim, that an entry of author `user` is the authority and an entry of author `assistant`
is context, and that a contradiction with what the user answered yes to is a contradiction with the
user's own words. A removal of code that only an assistant entry names is no prompt-versus-spec
conflict. The `no-words` trigger of the writing stages fires on a spec that was not supplied,
cannot be read, or holds no entry of author `user`.

The marked block of the main script holds values and no prose. The private record path, the
criteria count, the implementer prompt, the scoping and the invariants are gone from it, so no word
of the orchestrating session reaches a stage. The implementer's task is the closing line of its
prompt: implement what the following discussion arrived at, followed by the spec path, every entry
in its order. The cold alternatives reviewer receives the hygiene floor and the diff, like the
quality reviewer.

Correctness, spec compliance and the duplicate checker read the spec and return findings only, with
no verdicts. Each finding carries `words`, the user's words of the entry it is judged against, and
says in `claim` what the implementation gets wrong; the script retries and then fails a reviewer
whose finding leaves `words` empty. The other reviewers keep their schemas.

The implementer's spec findings quote the words of the spec entries they concern in `words`. The
classes are `joint-impossibility`, two statements of the user that cannot both hold,
`missing-contract`, `reality-drift`, and `unbacked-entry`, an entry whose words were said about
another unit. An `unbacked-entry` finding does not block the run and is handed to the root as
CRITICAL, as the class it replaces was. The finding verifier closes an `unbacked-choice` finding
with a rejection only on a citation of the form `spec entry <file>:<line>: "<quote>"`, which names
the entry by its session record.

## The fix run

A fix list has exactly two keys: `run`, the parent run's ID, and `findings`, a list of source IDs
of the parent run's findings. The spec tool resolves each source ID against the parent run's
journal, as before, and prints each finding as the journal holds it. The fix script receives that
output as its launch value, and its launch check hands it back to the tool with `--expect`, which
fails when any finding differs from the journal. Every stage of the fix run therefore works on what
the reviewer said, with no correction written by the orchestrating session.

The parent spec is a value of the fix script's marked block. The scope check classes the correction
each finding asks for, keyed by its source ID; the fixer receives the corrective findings with the
scope check's reasons, one key per source ID; and the diff check maps every change of the fix to the
source ID of the finding it carries out.

## Alternatives the user rejected

- Keeping a written spec under stricter rules was rejected: text the model writes into a spec
  invents decisions and bends the user's words, so the spec holds quotes and nothing else.
- A discussion that ends when the workflow starts was rejected, because the user adds words while a
  run is going and after it returns.
- A whole message in every unit it touches was rejected in favour of a substring of the message.
- Words typed into the spec file were rejected: the user only removes entries in the editor.
- Acceptance criteria with a verdict per criterion were rejected in favour of findings that quote
  the user's words.
- Corrections written by the orchestrating session in a fix list were rejected, so the fix run
  passes on what the reviewer said.
- A file path with a hash for a plan the user approved was rejected, because the content of a Write
  call already stands in the transcript.
- A separate new tool was rejected: the spec changes are carried through the existing spec tool,
  scripts, templates and skills.

## Open

- OPEN: the section of the visual-verification skill on implement-review-verify still has the root
  name the expected outcome in a criterion, write the before capture's name and a short scratch path
  into the unit spec, and state a visual defect's correction in a fix-list entry. None of these
  values has a place in a spec of quotes or a fix list of source IDs.
- OPEN: the rule that sends an open choice which is neither a product nor an architecture decision
  to a new unit no longer names how the choice the orchestrating session decides reaches that unit,
  since a spec holds only quotes.
- OPEN: the spec-provenance template still describes spec items and the private directive record.
  No script starts it, and removing an agent template needs a decision of its own.
- OPEN: older design records in this directory describe the spec of items, the private record and
  the per-criterion verdicts that this change replaces.
