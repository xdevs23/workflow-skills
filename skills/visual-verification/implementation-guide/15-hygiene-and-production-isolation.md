# Part 15: hygiene and production isolation

The harness is tooling. It does not change application behavior or stored data, does not need a
migration, and leaves the production build exactly as it was. The harness code is in one tracked
directory used only by the harness. Everything generated by the harness is written to the harness
directory inside the project cache, the location defined by `workflow-skills:local-cache`.

## One small implementation

The harness is kept small, with separate responsibilities: a thin command line, one component that
runs the lifecycle of the server and the engine, one data boundary, capture and comparison
utilities, typed scene modules and small synthetic fixtures. The initial scenes share these
mechanisms. The harness does not introduce a plugin platform, a background service, a database, a
component catalogue tool or a replacement component system.

The harness adds only the families of dependencies needed by its components, as development
dependencies of the project under the project lock. The reference added exactly three: the browser
automation library, a PNG codec and a pixel comparison library. It added neither a schema framework
nor an interface library. The harness is type checked with the type checker configuration of the
application, extended with the runtime types needed by the harness, so fixtures fail to compile when
the types of the application change.

## Artifacts

Every generated artifact is in the harness directory: captures with their images, receipts and
reports, comparisons, evidence sheets, source exports, the dependency caches keyed by lock, the
caches of the server process, the private home directory, downloads, samples and selections, local
scenes, engine profiles, optional traces and logs, and the scratch directories of the self-test
suite.

There are two exceptions. The caller may write an evidence sheet prepared for a pull request to the
directory prepared for the batch of pull requests, as described in part 12, which is also inside the
project cache. The scratch directory of a run, described in part 2, is in the system temporary
directory and is removed when the run ends. Only scene modules, synthetic fixtures and harness code
are tracked. Artifacts that contain sample data or screenshots are written with private
permissions.

Capture and comparison leave the version control state and the application files unchanged. They
leave every reference, index entry, branch and working tree file as it was, including the
translation files and existing tests read by a scene. The acceptance criteria in part 17 check this
against the starting revision.

Source exports and server caches accumulate with every run, one directory each, until someone
removes them by hand. The harness never deletes a capture or a comparison by itself.

## Other file watchers

Every file watcher in the project excludes the project cache. A development server, a test renderer
or a build watcher that watches the repository root otherwise sees every source export as a change.
In the reference, the development configuration of the application polled the repository root. A
test helper for server-side rendering reused that configuration and had to exclude the cache from
the watcher. Without that exclusion, the exports pushed the first server-rendered test past its
timeout. The adoption adds these exclusions to the watcher configurations of the project and changes
nothing else in them.

## Production isolation

Production code never imports a scene, a fixture, a harness entry or a harness library. The
production build does not contain test routes, branches for a test mode in application code,
replaced state stores, styling overrides for captures, substituted icons, hidden content or patched
product styles. Production routes, start-up, styles and data behavior are unchanged.

The production output is inspected for harness code as part of the verification of the adoption.
The full check of the project is run bare, the production build is produced, and the output is
searched for the harness entries, the scene and fixture modules and the harness libraries.

## Web realization in the reference

The reference had its harness in one tool directory with a separate environment lock. The component
entries of the harness were in a subdirectory reachable only through the server configuration, and
the automation and image libraries were development dependencies. The build produced one
single-file HTML output. The verification inspected that file for harness code. The exclusion added
to the watcher of the test renderer was the only change outside the harness directory besides the
added dependencies.

## Native and terminal realizations

A native harness puts its scenes, fixtures and harness entries in a test source set or a separate
test module not included in the release build. The harness libraries are test-only dependencies.
The inspection lists the classes or symbols of the release package and searches them for harness
code. A terminal harness has its scripts outside the installed package and checks the list of files
in the package the same way.
