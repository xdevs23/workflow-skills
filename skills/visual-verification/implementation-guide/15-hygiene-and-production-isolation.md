# Hygiene and production isolation

Harness is tooling. Does not change application behavior or stored data, does not need a migration,
leaves production build exactly as it was. Harness code in one tracked directory used only by
harness. Everything generated by harness written to harness directory inside project cache, location
defined by `workflow-skills:local-cache`.

## One small implementation

Harness kept small, with separate responsibilities: thin command line, one component running
lifecycle of server and engine, one data boundary, capture and comparison utilities, typed scene
modules, small synthetic fixtures. Initial scenes share these mechanisms. Harness does not introduce
any plugin platform, background service, database, component catalogue tool or replacement
component system.

Harness adds only families of dependencies needed by its components, as development dependencies of
project under project lock. Reference added exactly three: browser automation library, PNG codec,
pixel comparison library. Added neither schema framework nor interface library. Harness type checked
with type checker configuration of application, extended with runtime types needed by harness, so
fixtures fail to compile when types of application change.

## Artifacts

Every generated artifact in harness directory: captures with their images, receipts and reports,
comparisons, evidence sheets, source exports, dependency caches keyed by lock, caches of server
process, private home directory, downloads, samples and selections, local scenes, engine profiles,
optional traces and logs, scratch directories of self-test suite.

Two exceptions. Caller may write evidence sheet prepared for pull request to directory prepared for
batch of pull requests, also inside project cache. Scratch directory of a run in system temporary
directory, removed when run ends. Only scene modules, synthetic fixtures and harness code tracked.
Artifacts containing sample data or screenshots written with private permissions.

Capture and comparison leave version control state and application files unchanged. They leave every
reference, index entry, branch and working tree file as it was, including translation files and
existing tests read by a scene. Acceptance criteria check this against starting revision.

Source exports and server caches accumulate with every run, one directory each, until someone
removes them by hand. Harness never deletes capture or comparison by itself.

## Other file watchers

Every file watcher in project excludes project cache. Otherwise development server, test renderer or
build watcher watching repository root sees every source export as change. In reference, development
configuration of application polled repository root. Test helper for server-side rendering reused
that configuration, had to exclude cache from watcher. Without that exclusion, exports pushed first
server-rendered test past its timeout. Adoption adds these exclusions to watcher configurations of
project, changes nothing else in them.

## Production isolation

Production code never imports scene, fixture, harness entry or harness library. Production build
does not contain test routes, branches for a test mode in application code, replaced state stores,
styling overrides for captures, substituted icons, hidden content or patched product styles.
Production routes, start-up, styles and data behavior unchanged.

Production output inspected for harness code as part of verification of adoption. Full check of
project run bare, production build produced, output searched for harness entries, scene and fixture
modules, harness libraries.

## Web realization in the reference

Reference had harness in one tool directory with separate environment lock. Component entries of
harness in subdirectory reachable only through server configuration. Automation and image libraries:
development dependencies. Build produced one single-file HTML output. Verification inspected that
file for harness code. Exclusion added to watcher of test renderer: only change outside harness
directory besides added dependencies.

## Native and terminal realizations

Native harness puts scenes, fixtures and harness entries in test source set or separate test module
not included in release build. Harness libraries test-only dependencies. Inspection lists classes or
symbols of release package, searches them for harness code. Terminal harness has scripts outside
installed package, checks list of files in package same way.
